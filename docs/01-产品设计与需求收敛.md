# 01 · 产品设计与需求收敛

## 起点：三个工作流，一天五条消息

这个项目最初不是一个，是三个：

| 工作流 | 干什么 | 推送 |
|---|---|---|
| 考研哨兵 | 盯关键日期（准考证、初试、成绩）+ 抓官方通知 | 有就推 |
| 考研日课 | 每天四科任务和 120 分钟时间分配 | 每天 1 条 |
| 考研热点雷达 | 抓政策 → 押考点 → 推带背 | 有就推 |

三个都能跑，但合在一起是灾难：**一天最多 5 条消息，维护要开三个 Active 开关，内容互相重复**（哨兵的"准考证提醒"和日课的"今日任务"在同一天出现，用户要在两条消息之间自己对时间）。

## 重新定义问题

一开始我以为问题是"信息不够"，所以加了第三个工作流去抓政策。真正用过两周才发现问题是反的：

> **不是缺信息，是缺"今天到底干什么"这一句话。**

用户打开手机的那一刻，想知道的是三件事：今天练什么、今天背什么、有没有必须马上处理的事。这三件事被拆在 3 个入口、5 条消息里，等于把"整合信息"的成本又推回给了用户。

所以产品形态从"三个提醒器"改成"**一天两条日更**"。

## 收敛后的结构

```
每天 11:00（一个定时器，一个 Active 开关）

📚 考研日课    → 今天练什么：120 分钟分配 + 四科任务 + 变式题 + 情报 + 日期提醒条 + 官方通知
🌿 今日带背    → 今天背什么：政策主线 → 押题方向 → 库内必背原文 → 答题框架
```

分工是刻意的、不重叠的：

- **日课管「练什么」**——给动作、给时长、给题
- **带背管「背什么」**——给理论、给原文、给框架

两条消息在同一次执行里产出（5 个节点串成一条链），所以不存在"日课说今天背 A、带背推了 B"的错位。

## 三个工作流怎么被吃掉的

收敛不是简单合并，是重新分配：

**哨兵 → 拆成两半，都进日课卡片**

| 原能力 | 新位置 | 改进 |
|---|---|---|
| 关键日期提醒 | 卡片顶部红色提醒条 | 原来是一条独立消息，现在跟着日课一起来，不会漏看 |
| 官方通知抓取 | 卡片底部「📢 官方通知」区块 | 原来是单独推送，现在和当天任务同屏，看到任务就看到通知 |

顺带解决了一个原设计的硬伤：**哨兵只在当天推，错过就永久丢失**。改成卡片内区块后，日期提醒按"距今天数"计算展示，昨天没开机、今天打开仍然看得到。

**日课 → 保留，成为主干**
四科任务表、120 分钟分配、B 站情报抓取全部留下，作为日课卡片的骨架。

**热点雷达 → 变成带背，且换了内核**
原来是"抓政策 → 让模型写一段解读"。现在改成"抓政策 → 模型只选母题 → 背诵原文从库取"，具体见 [02-内容体系与 AI 边界](02-内容体系与-AI-边界.md)。

## 一个被砍掉的需求

原本还想做"每日一句鼓励""学习时长统计"这类留存功能，都砍了。

理由：这是一个**单人使用、目标是 50 天后考试**的产品，留存指标没有意义，有用性才有。每加一个模块都会稀释"今天干什么"这一句话的清晰度。**产品做到最后，加法不值钱，减法才值钱。**

## 交付节奏为什么是 11:00

不是拍脑袋定的。备考的一天通常是：早上起来先看今天干什么 → 上午数学 → 下午专业课 → 晚上政治英语。11:00 这个点，人已经在书桌前、但还没进入状态，这时候推"今天练什么"最容易被真正执行。

早期版本是 20:00，结果是"看到了，但今天已经过完了"。**推送时间本身就是产品设计的一部分。**

## 数字

| 项 | 收敛前 | 收敛后 |
|---|---|---|
| 工作流数量 | 3 个 | 1 个 |
| 每日消息条数 | 最多 5 条 | 固定 2 条 |
| Active 开关 | 3 个 | 1 个 |
| 节点数 | — | 5 个 |
| 每日推送时间 | 分散 | 11:00 一次 |
