# 03 · 降噪与推送设计

日均 59 条官方通知，用户真正需要的 1 条。这个项目的推送设计，本质上是**一个漏斗 + 一个防打扰机制**。

## 漏斗：59 条 → 1 条

三个源（研招网 ×2 + 招生单位官网）每天加起来 50~60 条。这些页面混杂着招生、竞赛、论坛、招聘、博士招生、本科招生、党建活动，真正跟"一个考生今年要做什么"有关的只有极少数。

实测（2026-10-30）：**59 条 → 保留 1 条**（招生单位的推免名单公示）。

过滤分三层，逐层收窄：

```
59 条
 │
 ├─ 第 1 层：噪声词丢弃（44 个词）
 │    大赛 / 竞赛 / 论坛 / 峰会 / 获奖 / 表彰 / 招聘 / 夏令营 /
 │    博士 / 直博 / 硕博连读 / 在职 / 非全日制 / MBA / 本科 /
 │    高考 / 专升本 / 自考 / 留学 / 雅思 / 宣讲 / 党建 ...
 │    —— 命中即丢，不问理由
 │
 ├─ 第 2 层：外省口径丢弃
 │    只保留「本省 + 全国」的政策。外省教育考试院发的
 │    "本省考生须知"，对本省考点的人毫无意义。
 │    （注意：含"教育部"字样的保留，全国口径要留）
 │
 └─ 第 3 层：他校招生宣传丢弃
       （同时命中"招生/专业目录/简章"，但不含本校特征的）
 │
 ▼
保留 1~2 条
```

**第 1 层用"丢"而不是"留"是个关键选择**：关键词白名单（NOTI_KEY 23 个字：准考证、考场、调剂、复试、国家线、网上确认……）只用来算权重，不用来决定生死。因为真实通知的措辞永远比你想的野——用白名单做主过滤，会静默漏掉真正重要的通知。

反过来，噪声词黑名单漏掉一条的代价只是"多看到一条不相关的"，可以接受。**在信息过滤里，宁可误留不可误杀。**

## 分档：重点 / 一般

过滤完剩下的还要排序。带「招生 / 考试 / 教育部 / 研究生院」这类词，或者来源本身就是招生单位的，标为**重点**排前面；其余标**一般**。

卡片上重点带 `[重点]` 前缀，用户扫一眼就知道哪条要先看。

## 不推空卡片

没有相关通知时，卡片底部只显示一行灰字：「今日无相关通知」。

这件事听起来小，但它是**信任**问题：如果一个推送渠道有 30% 的时候是空的，用户会开始忽略它；一旦开始忽略，真正重要的那条也会被划过去。**推送渠道的价值 = 每次推送的有效率，不是推送次数。**

## 时间窗：定时 21 天，手动 60 天

抓取按发布时间过滤，但两种执行模式用不同窗口：

| 模式 | 窗口 | 原因 |
|---|---|---|
| 定时执行（每天 11:00） | 21 天 | 正常日报，只看最近的 |
| 手动点执行 | 60 天 | 漏跑几天后补看，放宽窗口把之前的捞回来 |

这个细节来自真实故障：早期版本只有一个窗口，用户电脑关了三天再打开，中间的通知全丢了。**两种使用场景要两套参数，不能共用一套。**

## 防同质化：背诵台账

带背卡片上线一周后收到一条反馈：**"好多天都重复。"**

原因很清楚：模型每次只看到"今天的政策"，不知道"昨天背了什么"，于是同一批政策反复命中同一批母题。

改法是加一本**背诵台账**（`beibeiHistory`，保留 14 天）：

```
每次推送后：把当天选的母题 + 要点编号写进台账
下次运行：把最近 3 天的记录一起喂给模型，提示词里强制避开
兜底轮换时：挑最近 5 天没背过的母题、最近 3 天没背过的要点编号
```

这是典型的"产品问题不能靠提示词解决"——你可以写一百遍"不要重复"，但模型根本不知道什么是重复。**给它数据，比给它指令有效。**

## 每天只展开 1 个母题

早期版本一天展开多个母题，一条消息几千字。实测的结论是：手机上读不完，读完也记不住。

改成一个，理由不是省事，是**背诵的机制**：

> 背诵靠重复，不靠一次看全。

卡片形态也跟着做减法：**一张卡、把一个母题的全部要点铺开，不折叠、不放外链。** 折叠要多点一次才看得到正文，外链在微信里打开还得跳出应用——两个动作都在增加"今天算了"的概率，而背诵的时候手本来就要离开屏幕。

"其余母题去哪了"是另一半答案：它们不进当天卡片，但也不会丢，靠上一节的台账轮换到后面几天。目前能完整展开的母题是 9 个，这 9 个构成轮换池，池子轮完约 9 天；实际重复间隔由台账决定（模型避开最近 3 天、兜底避开最近 5 天）。另外 11 个能被政策召回、能押中方向，补齐详解后自动进入轮换（见 [05 的局限](05-定制与维护.md)）——**池子多大，周期才有多长。**`PICK_N` 就是"一次展开几个"这个旋钮。

## 一个真实的工程事故：2 万字上限

PushPlus 对实名用户的单条消息上限是 2 万字。某次内容量涨上来之后，接口返回成功、但微信收不到——实际是被静默拒收（实测 38252 字那条被 999 拒收）。

修复是在渲染后加一道**长度保险**：超过 1.8 万字时，在最近的 `</div>` 边界处切掉，末尾补一行"…（本期内容较长，已截断）"。宁可少背几条，也不能整条被静默拒收。

教训：**第三方通道的隐式限制必须显式兜住**。"接口返回 200"不等于"用户收到了"。
